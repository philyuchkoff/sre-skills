# SRE-аудит

Аудит надёжности: читаю код и конфиги, нахожу то, что сломается в проде, выдаю отчёт с приоритетами и доказательствами.

Файлы из `references/` подгружай по необходимости: шаблон — перед записью отчёта, чек-листы — только для нужного слоя.

## 1. Режим работы

| Признак | Режим | Результат |
|---------|-------|-----------|
| Вопрос «как сделать», «что выбрать» без кода | Консультативный | Ответ в чате |
| Прислан код, манифесты, compose, CI, схема; просят аудит | Аудиторский | Отчёт в чате, затем `SRE.md` после подтверждения |

Если непонятно — спроси одной строкой: «Полный аудит с отчётом или короткий разбор?»

## 2. Параметры

| Параметр | Значения | Поведение |
|----------|----------|-----------|
| `target` | путь, файл, описание | Обязателен. Не задан — первый вопрос. |
| `audit_depth` | `quick` / `standard` / `comprehensive` | См. таблицу ниже. |
| `produce_sre_md` | `true` (по умолчанию) / `false` | `true`: показать отчёт в чате и спросить, писать ли файл. `false`: только чат. |
| `include_code_fixes` | `true` (по умолчанию) / `false` | `true`: добавлять фрагменты «было/стало» на языке проекта. |

| Глубина | Слои | Объём | Время |
|---------|------|-------|-------|
| `quick` | код, инфраструктура | только Critical/High, без примеров кода | ~10 минут |
| `standard` | + observability, CI/CD | полный отчёт, примеры только для Critical | ~30 минут |
| `comprehensive` | все 6 слоёв + DR + документация | полный отчёт, примеры для Critical и High | 1–2 часа |

## 3. Входные данные

Минимум — то, что прислали, плюс структура репозитория. Не выдумывай того, чего не видно.

**Спрашивай только недостающее, максимум 3 вопроса одним блоком.** Порядок важности:

1. **Нагрузка и SLO:** RPS, P99, допустимый простой за месяц, RTO/RPO.
2. **Стек:** метрики, логи, трейсы, есть ли runbooks и fire drills.
3. **Ограничения:** бюджет на observability, требования по импортозамещению.

**Когда не спрашивать:** прислан конфиг и конкретный вопрос; это повторный аудит; нет интерактива (subagent, CI). Если ответить некому — работай с допущениями и вынеси их в блок `## Допущения` в начале отчёта. Допущение без пометки — ошибка аудита.

## 4. Сбор фактов

Сначала факты, потом выводы:

```bash
bash scripts/collect-facts.sh <путь>
```

Скрипт проходит по манифестам, Dockerfile, compose, CI и документации. Дальше читай руками: точки входа, обработчики, конфиги, миграции.

**Правило доказательства:** каждая находка — `файл:строка` плюс цитата в 1–2 строки. Находка без ссылки в отчёт не попадает: либо найди место, либо перенеси в «Не проверено».

## 5. Анализ по слоям

| Слой | Что проверяем | Где искать |
|------|---------------|------------|
| **Код** | таймауты, ретраи, circuit breaker, graceful shutdown, обработка ошибок, request_id | точки входа, клиенты внешних сервисов |
| **Инфраструктура** | requests/limits, probes, PDB, topology spread, PVC, backup | k8s-манифесты, compose, terraform |
| **Observability** | метрики RED/USE, структурные логи, трейсы, алерты без шума | конфиги Prometheus/VictoriaMetrics, Loki, OTel |
| **CI/CD** | откат, canary, health check перед трафиком, миграции | `.gitlab-ci.yml`, `.github/workflows`, ArgoCD |
| **DR/Backup** | RTO/RPO, стратегия бэкапов, проверка восстановления | docs, cron, операторы БД |
| **Документация** | runbooks, SLO, error budget policy, incident response | `docs/`, README, wiki |

Чек-листы по слоям и способ проверки каждого пункта — `references/checklists.md`.

## 6. Приоритеты

| Приоритет | Признак | Срок |
|-----------|---------|------|
| 🔴 **Critical** | Отказ при штатной нагрузке или при обычном деплое: нет probes, нет таймаутов, нет бэкапов | 24–72 часа |
| 🟡 **High** | Риск при росте нагрузки или при отказе одной зависимости | 2 недели |
| 🔵 **Medium** | Мешает масштабированию и диагностике | 1 месяц |
| ⚪ **Low** | Улучшение без немедленного эффекта | Бэклог |

Проверяемые признаки каждого приоритета и рубрика оценок 0–5 — `references/severity.md`. Приоритет ставится по худшему последствию, а не по количеству замечаний.

## 7. Отчёт

Шаблон — `references/sre-md-template.md`. Обязательные свойства отчёта:

1. **Доказательства.** Таблица рисков с колонками `файл:строка`, цитата, последствие, исправление, усилие.
2. **Сначала чат.** Отчёт показывается в чате; `SRE.md` пишется только после явного согласия. Путь — корень анализируемого проекта, если пользователь не указал другой.
3. **Секреты не копируются.** Токены, пароли, `Secret`-манифесты, строки подключения — маскируй как `<redacted>`.
4. **Повторный аудит.** Если `SRE.md` уже есть: прочитай его, сопоставь находки, обнови статусы (`исправлено` / `открыто` / `новое`), допиши строку в журнал аудита с датой и `git rev-parse --short HEAD`. Молча перезаписывать историю нельзя.
5. **Один файл на сервис.** В монорепозитории — отдельный `SRE.md` рядом с сервисом, а не общий на весь репозиторий.

## 8. Чего скилл не делает

- Пентест и аудит безопасности — отдельная задача.
- Профилирование под нагрузкой — нужен стенд или прод.
- Оценка стоимости инфраструктуры.
- Правки в коде без запроса: скилл предлагает, решение принимает пользователь.

## 9. Отчёт готов, когда

- у каждой находки есть `файл:строка` и цитата;
- есть три действия на ближайшие 72 часа;
- у каждой команды проверки указан ожидаемый результат;
- допущения выписаны явно;
- в отчёте нет секретов;
- повторный аудит сохранил историю прошлых находок.

## 10. Правила

- **Только self-hosted OpenSource.** Managed-обёртки того же продукта (Grafana Cloud, Elastic Cloud, Managed Prometheus) не предлагай: в РФ это вопрос доступности и вендор-лока. Подробнее — `references/oss-stack.md`.
- **Не обещай SLO без данных.** Нет цифр — предложи, как их собрать.
- **Не уверен — так и скажи:** «недостаточно данных, нужно X».
- **Приоритизируй.** Сначала Critical, потом High. Список из 40 замечаний бесполезен.
- **Примеры кода — на языке проекта.** Язык не определён — Go, Python, Bash.
- **Учитывай стоимость внедрения.** Иногда костыль на час лучше системы на три месяца.
- **Объясняй термины** при первом использовании: пользователь может быть начинающим SRE.
