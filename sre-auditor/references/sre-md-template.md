## 🔥 Реестр рисков

Одна таблица на все приоритеты. Сортировка: сначала приоритет, потом дешевизна исправления.

| Приоритет | Файл:строка | Что найдено | Доказательство | Последствие | Исправление | Усилие |
|-----------|-------------|-------------|----------------|-------------|-------------|--------|
| 🔴 Critical | `k8s/deploy.yaml:23` | нет readinessProbe | в `spec.containers[0]` только `image` и `ports` | трафик идёт в непрогретый под → 502 при rollout | добавить `readinessProbe` на `/ready` | S |
| 🟡 High | `internal/client/api.go:41` | клиент без таймаута | `http.Client{}` без `Timeout` | зависший upstream копит горутины | `Timeout: 3 * time.Second` | S |

Усилие: **S** — до часа, **M** — до дня, **L** — больше дня. Если находок больше 15 — оставь в таблице Critical/High, остальное вынеси в раздел «Бэклог».

## 📋 План внедрения

### ⚡ Немедленно (24–72 часа)

- [ ] закрыть Critical из реестра рисков;
- [ ] добавить `/health` (liveness) и `/ready` (readiness);
- [ ] настроить алерты на 5xx и задержку.

### 🟡 Краткосрочно (до месяца)

- [ ] структурные логи в JSON с `request_id`;
- [ ] распределённый трейсинг, сэмплирование 1%;
- [ ] chaos-эксперимент: убить под под нагрузкой.

### 🔵 Среднесрочно (3–6 месяцев)

- [ ] error budget на основе SLO (передать в `sre-slx`);
- [ ] автоматический canary с откатом;
- [ ] runbooks для топ-5 сценариев отказа.

## 🚨 Метрики и алерты, которых не хватает

| Метрика | Зачем | Порог | Действие |
|---------|-------|-------|----------|
| `service_errors_total` | без неё проблемы не видно | > 1% за 5m | смотреть логи |
| `queue_depth` | очередь растёт → скоро таймауты | > 100 за 1m | масштабировать консьюмеров |
| `upstream_request_duration` | внешняя зависимость тормозит | p99 > 500ms | включить circuit breaker |

## ⚠️ Слабое место этого аудита

Что не проверено и почему:

- реальное поведение под трафиком — нет прода или стенда;
- утечки памяти — нужен прогон под нагрузкой;
- корректность сэмплирования трейсов — нужны реальные данные.

Что усилит аудит:

- нагрузочный тест на staging;
- метрики за 7 дней;
- post-mortem последнего инцидента.

## ✅ Что проверить в проде прямо сейчас

У каждой команды — ожидаемый результат, иначе это не проверка, а гадание.

### Kubernetes

```bash
# поды и число перезапусков; ждём 0 у новых подов
kubectl get pods -o wide

# события проблемного пода; ждём отсутствие OOMKilled и FailedMount
kubectl describe pod <pod> | grep -A10 Events

# сработавшие алерты (Alertmanager через port-forward)
kubectl -n monitoring port-forward svc/alertmanager 9093:9093 &
curl -s localhost:9093/api/v2/alerts | jq '.[].labels.alertname'
```

### Docker Compose

```bash
# статус контейнеров; ждём healthy, а не только Up
docker ps --format "table {{.Names}}\t{{.Status}}"

# ошибки за последние 50 строк
docker logs --tail=50 <container> 2>&1 | grep -i error

# потребление ресурсов без потока
docker stats --no-stream
```

### Bare metal

```bash
systemctl status <service>

journalctl -u <service> -n 100 --no-pager | grep -i error

# порты и процессы; без sudo имена процессов не видны
sudo ss -tlnp | grep <port>
```
