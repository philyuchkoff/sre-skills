# Приоритеты и оценки

Как ставить приоритет и как считать зрелость, чтобы цифры в отчёте можно было защитить.

## Как выбрать приоритет

Приоритет ставится по **худшему последствию**, а не по количеству замечаний. Один отсутствующий таймаут важнее десяти отсутствующих аннотаций.

| Приоритет | Срок | Признаки (достаточно одного) |
|-----------|------|------------------------------|
| 🔴 **Critical** | 24–72 часа | Отказ при штатном деплое: нет readinessProbe или graceful shutdown. Отказ при штатной нагрузке: нет таймаутов на внешних вызовах, неограниченная очередь, работа без лимитов памяти с риском OOMKilled. Потеря данных: нет бэкапов или восстановление ни разу не проверяли. Единственная реплика критичного сервиса. |
| 🟡 **High** | 2 недели | Отказ одной зависимости роняет весь сервис: нет ретраев, нет circuit breaker, нет деградации. Нет PDB и topology spread при нескольких репликах. Алерты не настроены или их столько, что на них не смотрят. Логи без `request_id` в цепочке из трёх и более сервисов. Миграции без возможности отката. |
| 🔵 **Medium** | 1 месяц | Мешает диагностике и масштабированию: нет трейсов, метрики только «средние» без p95/p99, нет дашбордов. Ручной деплой без canary. Нет runbooks. Ретраи без jitter. |
| ⚪ **Low** | Бэклог | Косметика и удобство: единый формат дашбордов, аннотации, алерты на неиспользуемые метрики, дублирующиеся конфиги. |

Пограничный случай — ставь более высокий приоритет и напиши в отчёте, почему сомневался. Занизить Critical дороже, чем перестраховаться.

## Оценка зрелости (0–5)

Оценка ставится **по худшему признаку уровня**: если observability закрыта на 4, но алертов нет вообще — это 2, не 3.5.

| Оценка | Observability | Отказоустойчивость | DR/Backup | CI/CD | Документация |
|--------|---------------|--------------------|-----------|-------|--------------|
| **0** | ничего не собирается | нет ни таймаутов, ни ретраев | бэкапов нет | деплой руками | документации нет |
| **1** | есть логи в stdout | есть таймауты на части вызовов | бэкап есть, восстановление не проверяли | есть скрипт деплоя | README без runbook |
| **2** | логи + базовые метрики CPU/RAM | таймауты + ретраи без jitter | ежедневный бэкап, RTO не определено | CI собирает, но не деплоит | есть README и схема |
| **3** | RED-метрики + алерты на 5xx и задержку | + graceful shutdown и probes | бэкап по расписанию, RTO/RPO описаны | CI деплоит, откат вручную | runbooks для топ-3 отказов |
| **4** | + трейсы с сэмплированием, дашборды | + circuit breaker, деградация | восстановление проверяли хотя бы раз | canary или blue-green | + SLO и error budget |
| **5** | + USE-метрики, алерты без шума, SLI из коробки | + chaos-эксперименты в регулярке | регулярные учения, RTO подтверждён | автоканареечный откат по метрикам | + fire drills, post-mortem культура |

**Итоговая надёжность:**

- **Low** — есть хотя бы один Critical;
- **Medium** — Critical нет, есть High;
- **High** — Critical и High закрыты, остались Medium/Low.

## Что не считать находкой

Чтобы отчёт не разбухал:

- вкусовщина без последствий (стиль YAML, порядок полей);
- отсутствие «модных» практик (service mesh, GitOps), если задача решается проще;
- то, что нельзя проверить по репозиторию, — только в «Не проверено»;
- замечания, которые не меняют поведение системы под нагрузкой и при отказах.
