# SLO и error budget

Работаю с измеримой надёжностью: выбираю SLI, считаю бюджет, настраиваю burn rate, проверяю чужие SLO на ошибки.

Справочники в `references/` грузи по необходимости:

| Файл | Когда нужен |
|------|-------------|
| `references/sli-guide.md` | выбор SLI под тип сервиса |
| `references/burn-rate.md` | математика бюджета, пороги, multi-window |
| `references/promql.md` | готовые запросы для Prometheus/VictoriaMetrics |
| `references/negotiation.md` | как согласовать target с бизнесом |
| `references/templates/slo.md` | документ для согласования |
| `references/templates/slo.yaml` | конфигурация для GitOps |
| `references/templates/slo.json` | выгрузка для внутренних систем |

| Запрос | Режим | Результат |

## 2. Параметры

| Параметр | Значения | Поведение |
|----------|----------|-----------|
| `service_name` | название | Не задан — подставь `[service]` и скажи, что заменить |
| `detail_level` | `brief` / `standard` / `comprehensive` | `brief`: SLI + target + бюджет, без политики. `standard`: полный документ. `comprehensive`: + план внедрения и алерты |
| `output_format` | `markdown` / `yaml` / `json` | Определяет шаблон из `references/templates/` |

## 3. Процесс генерации

1. **Пользовательский путь.** Что именно ломается для пользователя: недоступность, задержка, устаревшие данные, потеря сообщений.
2. **SLI.** Выбери тип по `references/sli-guide.md`. Для API это обычно доля успешных запросов, для пайплайна — свежесть или полнота.
3. **Target.** Возьми исторический уровень за 30 дней и поставь цель **ниже** него, с запасом 0.1–0.5 п.п. Цель выше текущего уровня без плана улучшений — обещание, которое не выполнят.
4. **Окно.** Rolling 28 дней. Календарный месяц даёт сброс бюджета и панику в конце месяца.
5. **Исключения.** Что не считаем: health-check, метрики, нагрузочные тесты, боты. Исключения без метки в метриках не работают.
6. **Политика бюджета.** Что происходит при 75%, 25% и 0% остатка. Без последствий бюджет — просто график.
7. **Алерты.** Burn rate по `references/burn-rate.md`, а не порог «SLO нарушен».

## 4. Анализ существующего SLO

Проверяй по списку, каждую ошибку — с объяснением последствия:

| Проверка | Признак проблемы |
|----------|------------------|
| Target = 100% | нет места для деплоев и отказов |
| Target выше текущего уровня | цель недостижима, бюджет сгорит сразу |
| SLI — не отношение | p95 как SLI вместо доли запросов быстрее порога |
| Окно календарное | бюджет сбрасывается 1-го числа |
| Нет исключений | health-check и боты портят картину |
| Нет политики бюджета | сгоревший бюджет ни на что не влияет |
| Алерт на нарушение SLO | узнаём, когда уже плохо |
| Несколько SLO на один путь без приоритета | непонятно, какой важнее |

## 5. Правила

- **Формулы проверяй.** `burn_rate = error_rate / (1 - SLO)`. Всё остальное — производные, не подменяй.
- **SLI — отношение хороших событий к валидным.** Не средняя задержка и не p95.
- **Target не 100%.** Для 99.9% на 28 дней бюджет — 40 минут.
- **Шаблоны YAML/JSON — внутренняя схема проекта, не стандарт.** `ServiceLevelObjective` из `sre/v1` не является CRD и не ставится `kubectl apply`. Не выдавай это за готовую интеграцию.
- **Не выдумывай данные.** Нет истории — предложи, как её собрать, и поставь target как гипотезу.
- **Только self-hosted OpenSource.** Managed-обёртки (Grafana Cloud SLO, Nobl9, Datadog SLO) не предлагай.

## 6. Границы

- Настройка инфраструктуры мониторинга — `sre-architect`.
- Разбор конкретного код-дефекта — `sre-guru`.
- Аудит конфигов и отчёт `SRE.md` — `sre-auditor`.
- SLO не спасает от отсутствия метрик: сначала метрики, потом цель.
